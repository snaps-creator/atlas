# Массовая проверка Atlas: исправление и границы замеров

Исследована рабочая копия поверх `4a6ed36` с уже существовавшей
незакоммиченной доработкой восстановления. Эти посторонние изменения сохранены.
Установленное приложение на машине — отдельная сборка 3.0.2; оно не заменялось.

## Путь проверки и найденные задержки

`main.tsx::testAll` подписывается на события и вызывает `latency_batch`.
`lib.rs` получает снимок настроек, затем использует работающую службу или
изолированное ядро без TUN. Каждая проверка вызывает Mihomo
`GET /proxies/{name}/delay`. Результаты доставляются по событиям, затем
подтверждаются итоговым ответом. До исправления очередь имела шесть работников.
250 неответивших узлов занимают примерно 42 последовательные волны ожидания.
Начало работы дополнительно разносилось искусственными паузами до 100 мс.

При работающем VPN каждый работник отдельно отправлял задание службе и
опрашивал `delay_result` раз в 150 мс. Все сообщения проходят через один
защищённый канал с mutex; команда службы при отсутствии сообщений ждёт 30 мс.
Увеличение только числа работников поэтому сохраняло бы лишние последовательные
IPC-запросы и конкуренцию со служебными чтениями.

История: `3ef3200` добавил короткий проход 1500 мс, затем второй полный проход
10000 мс для неответивших узлов. Это лишние соединения и ожидание перед полным
завершением. В исходной рабочей копии второй проход уже фактически отключён:
весь batch получал 1500 мс, что могло ошибочно отбрасывать рабочие медленные
узлы. Более того, новый статус `timeout` не соответствовал старому условию
повтора `unreachable`. Это не доказательство даты возникновения регрессии
установленной 3.0.2: её сквозной замер здесь не выполнен.

## Исправление

- До 64 параллельных запросов, один полный запрос на каждый узел, таймаут 10000 мс.
- Удалены второй проход и искусственная задержка запуска работников.
- Служба принимает несколько заданий и возвращает несколько готовых результатов
  за один IPC-обмен (`delay_many`, `delay_results`). Освободившиеся места
  заполняются без ожидания самого медленного узла. Прежние одиночные команды
  сохранены. Проверка разрешённых URL и ограничение размера пакета действуют.
- Общий предел сетевых запросов — 72, заданий службы — 80; это оставляет запас
  относительно одного ручного batch из 64. Очередь операционных чтений отдельная.
  Логика, частота и порог автоматического выбора не менялись.
- Убрано копирование одного измерения на другие имена с одинаковой конфигурацией:
  каждое имя списка получает собственную проверку.
- Фоновое чтение истории не заменяет ожидающий (`queued`) результат массовой проверки.
- Карточки показывают измерение числом с «мс», включая 0 и 210 мс, без
  «Устарело», «выше порога» и прочерков вместо пинга. При отсутствии результата
  используются уже существовавшие подписи; последнее успешное значение не
  подставляется вместо неудачного нового измерения. CSS не изменялся.

## Сопоставление с Clash Verge Rev

Проверены актуальные исходники GitHub, а не предположение о поведении интерфейса:

- [Clash delay manager](https://github.com/clash-verge-rev/clash-verge-rev/blob/main/src/services/delay.ts):
  `checkListDelay` фактически ограничивает параллельность 10 запросами,
  несмотря на значение аргумента по умолчанию 36. `measureDelay` запускает
  новый запрос; cache/history для отображения не заменяют ручное измерение.
  Есть случайная пауза до 200 мс и минимальное время индикации 500 мс.
- [Плагин Mihomo](https://github.com/clash-verge-rev/tauri-plugin-mihomo/blob/main/src/mihomo.rs):
  `delay_proxy_by_name` асинхронно ожидает прямой запрос к API ядра через
  HTTP или локальный сокет. Отдельного цикла service-job polling, как у Atlas,
  в этом пути нет.
- [Mihomo URLTest](https://github.com/MetaCubeX/mihomo/blob/Meta/adapter/adapter.go):
  HTTP HEAD через конкретный узел. При `unified-delay` выполняется повторный
  запрос по открытому соединению; измеряется его задержка, если он успешен.
  Atlas уже использует тот же URL Cloudflare и `unified-delay: true`.

Следовательно, быстрая выдача числового RTT не означает ожидание всего таймаута
или запуск всех узлов одновременно. Сравнение с конкретным установленным
Clash и его текущим набором/URL не выполнено.

## Измерения

Результаты: `BATCH-CHECK-MEASUREMENTS-2026-10-14.json`.
Сохранённая база открыта только для чтения; DPAPI расшифровывается в памяти.
Один и тот же fingerprint всех 250 узлов во всех прогонах; сетевые настройки
и активная VPN-сессия не изменялись. Mihomo до/после идентичен по SHA-256.
Таймер включает запуск и остановку изолированного ядра, все запросы и получение
всех результатов; чтение базы, UI и действующая служба в этот таймер не входят.

| Последовательный прогон | Полное время | Проверено | Успех / timeout / unreachable |
|---|---:|---:|---:|
| До, 6 работников, 1500 мс | 64,944 с | 250/250 | 1 / 248 / 1 |
| После, 64 работника, 10000 мс | 41,883 с | 250/250 | 2 / 247 / 1 |
| До, повтор | 64,971 с | 250/250 | 1 / 248 / 1 |
| После, повтор | 41,819 с | 250/250 | 1 / 248 / 1 |

Ни в одной паре ранее успешный узел не потерян. Все имена получили итоговый
результат; timeout не сокращён, а восстановлен до полного. Однако это не
доказательство скорости на рабочем пуле пользователя: почти все запросы здесь
достигли таймаута. При активном VPN служба разрешает прямой выход своим
исполняемым файлам из защищённого `ProgramData/Atlas-session-*`; изолированное
ядро из репозитория/каталога установки не воспроизводит этот путь. Причина
массовых таймаутов отдельно не доказана. Замена пути на идентичное ядро из
каталога установленного приложения существенно не изменила картину.

Первый окончательный ответ в этих прогонах: до 3,143/3,186 с, после
11,743/11,662 с. Он не обязательно успешный. Полный проход ускорился в этих
условиях, но мгновенный первый ответ на рабочем пуле не подтверждён.

Опциональный `latency::tests::real_batch_profile` воспроизводит сравнение:
`ATLAS_BATCH_DATABASE` задаёт read-only базу, `ATLAS_BATCH_CORE` — путь ядра,
`ATLAS_BATCH_POLICY=before|after` — замороженную прежнюю или текущую политику.
Тест игнорируется при обычном запуске и не является настройкой приложения.

## Проверки

- Frontend: 42 теста, включая рендер карточки с 0/80/210/1500 мс,
  отсутствие трёх нежелательных вариантов, отсутствие подстановки `lastDelay`.
- `npm run build`: успешно.
- Native: 190 тестов прошли, 2 opt-in профиля пропущены.
- Локальный HTTP-контроллер возвращает успешный ответ через 1700 мс:
  batch сохраняет его и публикует быстрый узел раньше, без повторной проверки.
- Named pipe: 67 узлов, задержанный первый результат, пополнение следующей
  волны, сохранение всех результатов, различение HTTP 504 и ошибки управления;
  всего два пакетных опроса вместо отдельных опросов каждого узла.
- Переполненная очередь URL-проверок не забирает операционную ёмкость.

Изменения подготовлены в исходниках. Сборка установленного приложения,
перезапуск его службы, замена установщика и публикация не выполнялись.
