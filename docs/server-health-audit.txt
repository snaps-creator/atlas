ATLAS — достоверность проверки серверов
Дата: 15 октября 2026, Europe/Moscow

1. ROOT CAUSE

Подтверждена ошибка критерия успеха, усиленная независимыми источниками UI.
До исправления latency::display_probe вызывал /proxies/{name}/delay без
expected=204 и принимал любой u64 delay. verified_probe, используемый монитором
и восстановлением, дополнительно проверял per-URL alive. В Mihomo 1.19.31
URLTest возвращает delay даже при несовпадении ожидаемого HTTP-статуса:
ошибка статуса отражается в extra[url].alive, но не в возвращаемом delay.

Старый regression-тест recovery_accepts_one_working_control_and_encoded_names_on_real_vless
прямо требовал display.status == "ok" после ответа HTTP 503 контрольного
сервера. Он заменён проверкой отказа без delay; новый вариант проходит.

ActiveServer читал историю ядра отдельно от карточек. Карточки хранили
ручной результат без TTL; завершение всей пачки повторно проставляло Date.now()
даже давно завершённым узлам. Общего порядка между ручными проверками,
пакетными результатами и монитором не было.

Также unified-delay=true измерял повторный запрос; ошибка этого запроса могла
быть проигнорирована при успешном первом. Это не измерение всей операции
с установлением соединения.

2. CODE EVIDENCE И ПРОВЕРКА ДЕВЯТИ ГИПОТЕЗ

Первичные исходники ядра:
  third_party/mihomo-v1.19.31-source.tar.gz:
    adapter/adapter.go: Proxy.URLTest
    hub/route/proxies.go: getProxyDelay
  https://raw.githubusercontent.com/MetaCubeX/mihomo/v1.19.31/adapter/adapter.go

1) Старый кэш задержки: подтверждено. Прежние src/latency.ts historyLatency
   и src/main.tsx не ограничивали возраст успешного результата. Итог пачки
   обновлял время получения всех результатов на время завершения пачки.
2) Только TCP connect: не подтверждено для URLTest. В исходнике есть
   p.DialContext, HTTP HEAD через полученное соединение, чтение ответа.
   Проверки локальных слушателей при старте Core — отдельный механизм.
3) DIRECT вместо прокси: для конкретного обычного Mihomo-адаптера URLTest
   обходит таблицу правил и вызывает этот адаптер. Для полного Xray-профиля
   controlled_profile сохранял provider routing; DIRECT действительно мог
   ответить через его SOCKS-вход. Это воспроизведено реальным Xray в новом тесте.
4) Другой outbound: URI-профили уже разделены namespace_simple и правилами
   inboundTag. Полные профили сохраняли правила/балансировщики и не давали
   гарантии конкретного outbound. Теперь у них отдельный проверочный вход,
   принудительно направленный в первый конкретный proxy-outbound профиля.
5) Успешный запуск Xray вместо теста: не подтверждено в latency. Core.running
   проверяет локальную сессию, а latency отдельно выполняет запрос.
6) Игнорирование ошибки реального подключения: в Recovery::tick ошибка
   приложения логировалась отдельно и не изменяла карточку. Такое событие
   теперь сохраняется отдельно от HTTP-проверки и инициирует свежий монитор.
   По одному сбою приложения нельзя объявлять неработающим весь прокси.
7) Перезапись новыми/старыми async-результатами: подтверждено отсутствие
   общего порядка. Ранее batchId, node identity и LatencyEpoch защищали только
   часть путей. Добавлены поколения конфигурации, operationId, startedAt,
   последовательность проверок одинакового node+URL и проверка актуальности
   перед публикацией. Разные контрольные URL могут выполняться параллельно.
8) Расхождение активного сервера и списка: подтверждено двумя источниками.
   Теперь оба компонента получают один объект Latency из родителя; /proxies
   содержит авторитетное atlasHealth, а сырая история не используется для UI.
9) STUN как отказ TCP: в исходной latency-цепочке STUN не использовался;
   общего критерия отказа STUN/TCP не найдено. TCP-проверка теперь явно имеет
   udp=untested. Ошибки пользовательских TCP/UDP-соединений хранятся отдельно.

3. FIXES И ЦЕПОЧКА ПРОВЕРКИ

Ручная/пакетная проверка либо существующий монитор
 -> имя узла и hash его фактической конфигурации
 -> общая State в Core/службе, generation и operationId
 -> блокировка только данного node+контрольного URL
 -> конкретный Mihomo-адаптер; для полного Xray отдельный authenticated SOCKS
    inbound с первым правилом inboundTag -> конкретный proxy outboundTag
 -> p.DialContext: транспорт и proxy-handshake
 -> HTTPS HEAD к cp.cloudflare.com/generate_204?atlas_probe=1
 -> проверка HTTP 204 через private per-URL health; редиректы не принимаются
 -> delay всей успешной операции, unified-delay=false
 -> публикация только если поколение и operationId всё ещё актуальны
 -> единый atlasHealth и одинаковое отображение в карточке/активном сервере.

HTTPS — основной отображаемый тест; прежний HTTP endpoint оставлен вторичным
диагностическим контролем. Его успех не подменяет зелёный основной результат.
TLS аутентифицирует контрольный endpoint; это не тест всех ресурсов Интернета.

При отказе delay=null, сохранены error/errorKind. HTTP 504 — timeout;
HTTP 503 от API — proxy_or_transport (ядро не всегда различает handshake,
reset и другие причины в HTTP API); неожиданный ответ — unexpected_response;
неподтверждённый маршрут — outbound_unverified; локальные сбои — controller.
Подробный контекст ядра остаётся в существующих диагностических логах.

Успех актуален 10 секунд. Начало новой проверки снимает старое положительное
утверждение. Изменение конфигурации, остановка и смена сети инвалидируют
состояние. Rollback восстанавливает прежние параметры с новым поколением,
не восстанавливая прежний положительный результат без проверки.

Раздел Servers запрашивает свежую пачку при открытии и по существующему UI
таймеру с интервалом 10 секунд, без перекрытия пачек. TUN-монитор службы
сохранил интервал 10 секунд. Для system-proxy режима применяется тот же
существующий UI-планировщик. Незавершённая большая пачка не запускается снова
каждые 10 секунд: устаревшие значения остаются неактуальными до нового теста.
В пакетной проверке максимум 6 работников; общий допуск ядра — 8 URL-тестов.
При смене подписки/режима прекращается запуск оставшихся старых заданий;
уже выполняющиеся запросы ограничены своими deadline, результаты отбрасываются.

Дизайн, размеры, CSS, навигация, параметры протоколов и пользовательские
правила маршрутизации не менялись. В существующих tooltip уточнена область
доказательства и отдельно показана последняя наблюдавшаяся ошибка приложения.

5. NETWORK VERIFICATION И ОГРАНИЧЕНИЯ

Сетевые тесты запускались вне песочницы после ошибки Windows 10013 в sandbox.
Они использовали изолированные loopback-порты, не включали пользовательский TUN
и не переключали системный прокси/DNS. Первоначальная блокировка не засчитана
как успешный тест. Для Vitest TEMP перенаправлен в рабочую папку после EPERM
на rename во временном каталоге sandbox; из поиска исключена архивная копия t/.

На одном промежуточном прогоне старый тест 50 циклов запуска остановился на
локальном controller timeout в цикле 44; на полном прогоне до него и следующем
полном прогоне тест прошёл. Неустойчивость этого прогона сохранена в rust-probes.log,
не скрыта и не приписана отказу удалённого сервера.

Рабочая подписка/удалённые серверы пользователя не использовались. Тест
supplied_vless_subscription_reaches_https_after_refresh_and_restart оставлен
ignored: требует ATLAS_VLESS_TEST_FILE. Три существующих updater-теста
restricted-user также ignored (дочерние драйверы и отдельный admin-only прогон).
Проверки всех транспортов Xray включают валидацию конфигураций реальным бинарником;
это не утверждение об end-to-end проверке каждого транспорта на удалённом сервере.
Причина реальных отключений конкретного провайдера этим аудитом не установлена.

Для полного JSON-профиля результат относится к первому конкретному proxy-outbound;
его tag сохранён в результате и tooltip. Успех не подтверждает все ветви правил,
все члены балансировщика и состояние каждого пользовательского соединения.
Профиль без конкретного поддержанного proxy-outbound не получает зелёный статус.
События реальных соединений берутся из доступных логов ядра: это диагностическое
наблюдение, а не полная инструментализация каждого потока/UDP-приложения.

8. FINAL VERDICT

Зелёный latency в исправленной сборке означает: не старше 10 секунд, успешный
контрольный HTTPS-запрос с ожидаемым HTTP 204 через указанный конкретный proxy
outbound текущей конфигурации. Значение включает установление соединения и
handshake. Отказ, stale, неподтверждённый маршрут и поздний результат не могут
сохранить прежнее число как текущий успех.

Это не гарантия UDP/STUN, всех сайтов, полной схемы маршрутизации сложного
профиля или непрерывной исправности произвольного пользовательского соединения.
Изменения внесены и собраны в рабочей копии; установленное приложение и служба
автоматически не заменялись.
