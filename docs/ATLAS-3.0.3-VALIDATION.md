# Atlas 3.0.3 — проверка актуальности пинга и подписок

Дата: 2026-10-14. База: `main`, `e71075b`; ветка `fix/atlas-3.0.3-auto-refresh`.

## Причина и соответствие сборок

На компьютере запущен установленный Atlas 3.0.2 из `Program Files/Atlas/versions/3.0.2-51c1e1664a1d548777ce61a1fc4645f3f2641602/Atlas.exe`. Это более ранняя сборка, чем исходный `main`: изменения массовой проверки из PR #63 в неё не входили. Рабочее дерево пользователя на `release/2.4.2` содержало постороннее изменение `update_user.rs`; работа выполнена в отдельном worktree, этот файл не изменялся.

В исходном коде чтение истории Mihomo выполнялось каждые 5 секунд только на странице Servers при активном подключении. Чтение истории не запускало новые измерения. Ручная проверка создавала отдельный проход. После 30 секунд успешный результат терял актуальность; новый проход автоматически не начинался. У установленной сборки это приводило к «Устарело», а более новый `main` уже оставлял старое число. В обоих случаях отсутствовал владелец непрерывных измерений на уровне приложения.

Обновление подписок уже имело общий фоновый поток и ограничение двух загрузок. Однако признак неудачи был константой `false`: недавняя ошибка не запускала повтор через 120 секунд. Старт принудительно загружал даже ещё свежие подписки. Условные HTTP-запросы и безопасное различение пустого списка и повреждённого ответа отсутствовали.

## Итоговое поведение

- Один координатор живёт вместе с Atlas, независимо от React, страниц и трея. На старте он ставит сохранённые профили в очередь; ручная проверка использует ту же очередь. Есть не более одного прохода и одной записи на профиль. Обрабатывается весь каталог, старые задания имеют приоритет.
- Успех повторяется через 15 секунд после завершения, ошибка через 10 секунд. Свежесть — прежние 30 секунд, таймаут сетевого HTTP-замера — прежние 10 секунд. Планировщик просыпается каждые 250 мс. Используется существующий предел 64 исполнителя, проверенный сравнением с 16 и 32.
- Пинг — HTTP delay Mihomo через конкретный профиль до `http://cp.cloudflare.com/generate_204`, с существующей методикой прогрева. Очередь не входит в числовой delay. Нет ICMP-подмены, переключения выбранного сервера или изменения TUN, TLS, Firewall/WFP.
- Завершённые ответы публикуются сразу. UI читает общий снимок по событию, при фокусе/навигации и раз в секунду. Скрытый UI не владеет сетевыми проверками. Возраст дополнительно проверяется при отображении.
- Число показывается только для свежего успешного замера, в том числе выше пользовательского порога (например, 1501 мс). Для ошибки, отсутствия данных и истечения срока область пуста. Подписи «Устарело», «выше порога», прочерки и новые статусы не выводятся.
- Идентичность включает источник и сетевые параметры, но исключает оформление имени. Ответы привязаны к идентичности, поколению сети и попытке. Удаление/изменение профиля, смена uplink, session/core PID, разрыв часов после сна инвалидируют прежние ответы. Новая подтверждённая ошибка скрывает прежний успех. Чтение, постановка в очередь и HTTP 304 не продлевают время успешного пинга.
- Подписки обновляются при наступлении срока: по умолчанию 1800 секунд, либо существующий интервал провайдера 1–720 часов. После ошибки повтор через 120 секунд; `Retry-After` дополнительно откладывает запрос. Две загрузки максимум; существующие сетевые таймауты 30 секунд без fallback и 9 секунд на адрес с fallback сохранены.
- ETag/Last-Modified действуют только для того же URL и User-Agent. HTTP 304 сохраняет отметку проверки, не заменяет серверы и не создаёт конфигурационные резервные копии. Частичный/повреждённый ответ сохраняет старый каталог; только явное `proxies: []` означает пустой список. Ошибка источника не превращает его серверы в недоступные.
- Новые/изменённые сетевые конфигурации проверяются заново; неизменённые сохраняют идентичность, избранное и ещё свежий пинг. Работающий сеанс и пользовательские правила выбора сохраняются.

## Реальные сетевые измерения

Выполнены на этом компьютере, из сети пользователя. Прочитан только зашифрованный снимок сохранённого каталога, 187 профилей. Секреты, адреса подписок, базы и полные журналы в Git не включены. Использовалось отдельное ядро без TUN с разрешёнными установленными бинарниками; рабочий Atlas и его соединение не переключались.

Все сравнения ниже использовали один снимок, весь список и один endpoint. `before` воспроизводит алгоритм установленного `51c1e16`: 6 исполнителей, первый дедлайн 1500 мс, повтор только `unreachable` (ошибочно исключавший `timeout`). Это сравнение с установленной сборкой, а не заявление об ускорении относительно PR #63, где 64 исполнителя и полный таймаут уже появились.

Существенного сдвига медианы от параллельности в этих проходах нет. Это наблюдения меняющейся сети и неодинакового множества успехов, не эталон абсолютной точности; время очереди отдельно отражено в длительности прохода.

Охват в каждой строке 187/187. CPU/память измерены с шагом 200 мс для теста и его непосредственных дочерних процессов; это приближённые измерения, не профилирование всей системы. Максимум четыре процесса в каждом проходе, роста не наблюдалось. Сетевые ответы могут меняться между проходами; одинаковое количество успехов не доказывает неизменность удалённой сети. Метод числового пинга не менялся.

Реальный координатор проработал 75,296 секунды: 187/187 профилей, минимум три завершённые попытки каждого, первый результат 1,216 секунды; в конце 153 успеха, 34 timeout. Очередь не превышала 187, после остановки осталось ноль временных каталогов ядра. Максимальный возраст успешного результата в снимках — 29,997 секунды. Максимальный возраст завершённого результата вообще — 35,654 секунды: при длинной очереди были кратковременные просроченные результаты (183 наблюдения «профиль × выборка», шаг 200 мс); они скрывались и автоматически обновлялись. Это не обещание непрерывного числа для каждого сервера и не многочасовой soak-тест.

На управляемом loopback-стенде настоящий поток работал 65,143 секунды, прошёл старую границу 30 секунд дважды: пять запросов, первый ответ 100 мс, максимальный возраст 15,007 секунды, десять событий. Страницы/окна в этом тесте нет.

## Автоматические и прикладные проверки

- Frontend: 63 теста, 15 файлов; production build успешен. Проверяются пустые ошибки, низкий/высокий пинг, истечение срока, неверный timestamp, смена probeId, последовательные IPC-чтения, повтор после ошибки и остановка UI.
- Release/updater contracts: 51 тест. Версии package, Cargo, Tauri и readiness согласованы на 3.0.3; история и зависимости не переписаны.
- Native: 389 успешно пройденных тестов (271 + 50 + 65 + 3), полный набор библиотеки и бинарников; управляемые часы, дедупликация, справедливое покрытие, быстрый ответ при медленном соседнем, отказ старых ответов, сетевые identity, подписки/избранное/выбор, миграция и сохранение данных. Отдельный реальный HTTPS-стенд проверяет 200→304, 401/403/429/503, Retry-After, неверное/пустое содержимое и явный пустой каталог. Сертификат доверен только клиенту теста, системные настройки не меняются.
- В отдельном реальном окне CEF собранного Atlas проверяется цепочка native IPC → модель → карточка: 43/1501 мс, ошибка после успеха, 321 мс, истечение срока, восстановление; четыре фазы и три перехода между страницами. Это управляемые значения IPC, а не выдаваемые за реальные сетевые замеры. Реальные сети проверены отдельно выше.
- Сон/скачок часов, смена сети, перезапуск ядра, удаление/замена профиля и поздние результаты проверены управляемыми тестами. Физический сон компьютера и отключение рабочего пользовательского туннеля не выполнялись. Многочасовая работа в трее не проверялась.

## Сборка, CI и откат

Штатный путь: `scripts/build-release-installer.ps1`, затем проверка transactional payload и запуск отдельного приложения через `scripts/test-ui-startup.ps1`. Локальная сборка не подписана релизным ключом, не опубликована и не установлена пользователю. Подписанный установщик и реальные upgrade-сценарии legacy/2.4.2 выполняются PR workflow `Verify connected upgrade` на disposable Windows runner. Локальный сценарий запрещает такой тест на машине с рабочей службой; этот предохранитель не обходился.

PR остаётся draft до успешных обязательных проверок. Ни тег, ни релиз, ни слияние не выполняются. Для отката исходников — revert коммитов PR; для уже установленного кандидата используется существующий transactional rollback. Сброс настроек, удаление подписок или обход защиты для отката не требуются.
