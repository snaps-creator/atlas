# Сетевой слой — 18 сентября 2026

Статус: код изменён, системный критерий готовности ещё не подтверждён.

## Подтверждённые причины

- Основной режим был `system`: Windows System Proxy не перехватывает весь IPv4, UDP и приложения, игнорирующие этот прокси. В предыдущем живом прогоне `TUN=False`.
- Генератор TUN безусловно заменял последний маршрут на `MATCH,ATLAS`, игнорируя значение пользовательского default-route.
- WFP-фильтры были постоянными и намеренно оставались после аварии. Это противоречило запрошенному автоматическому восстановлению.
- Проверка TCP искала соединение после завершения запроса, а UDP/Telegram не требовали доказательства входа через TUN. Наличие маршрута и ответ DNS не доказывают отсутствие утечки.

## Изменения

- Основной режим и миграция загруженных настроек — TUN. Подключение больше не включает Windows System Proxy; восстанавливается старый снимок прокси Atlas.
- Захват IPv4/IPv6 сохраняется; MATCH формируется из default-route. Исключения direct/proxy/block, domain-suffix, ip-cidr и no-resolve сохраняются. Формат YAML version: 1 не изменён, новых правил по процессам нет.
- При выключенном IPv6 первой идёт блокировка IPv6 в ядре. WFP разрешает приложениям только loopback и TUN; исходящие соединения ядра разрешены для работы транспорта VPN и DIRECT.
- Перехват DNS TCP/UDP:53 и upstream через ATLAS сохранены. Direct DNS использует те же upstream; ICMP forwarding напрямую отключён. Bootstrap для имён серверов VPN использует DoH вне туннеля.
- Защита WFP теперь принадлежит динамическому сеансу helper. При отключении сначала закрывается core, затем защита. Авария helper освобождает динамические фильтры Windows; авария core/родительского UI завершает helper. Поведение реальных маршрутов и DNS после аварии требует живого теста.
- Добавлены ожидание интерфейса при старте и обновление привязки WFP после применения конфигурации.
- Диагностика TCP/UDP наблюдает новые потоки во время запроса, требует TUN → ATLAS, сопоставляет исходный порт STUN. Telegram требует наблюдаемые TUN-соединения с полученными данными; это не заменяет проверку всех функций клиента.
- DNS проверяется новым запросом с уникальным именем. DNS leak и IPv6 leak остаются непроверенными без захвата пакетов; не показываются как успешные по косвенным признакам.
- Кнопка «Очистить» удаляет результаты проверок; ответы старого запуска не восстанавливают очищенный список.

## Выполненные проверки

- Rust: 31 тест прошёл. В том числе запуск реального Mihomo `-t` для пустого full-tunnel YAML, IPv6 on/off и исключений domain-suffix/direct, ip-cidr/block/no-resolve.
- Frontend: 6 тестов прошли; проверка TypeScript и Vite включена в release-сборку.
- Существующий тест отдельного локального proxy/TCP/UDP исключён из этого прогона: использует фиксированные порты запущенного Atlas. Результаты прежних запусков не выдаются за системную проверку новой версии.

## Оставшийся системный прогон

Нужны права администратора, отсутствие конкурирующего TUN и резервный способ восстановления связи. Не заменять пользовательские правила без резервной копии; на время теста использовать `version: 1`, `default-route: proxy`, `rules: []`, затем восстановить их.

1. Сопоставить новые IPv4/TCP и UDP/STUN потоки с TUN → ATLAS и внешним ответом.
2. Проверить literal IPv6 и AAAA; при выключенном IPv6 убедиться в отсутствии физических исходящих пакетов.
3. Захватить физический интерфейс для свежих DNS-запросов TCP/UDP и проверить отсутствие прямого 53/853. Проверить upstream DNS через VPN отдельно от bootstrap VPN-сервера.
4. Отключить встроенный прокси Telegram; проверить загрузку и передачу данных клиента через TUN.
5. Проверить direct/proxy/block по domain-suffix и ip-cidr с реальными ответами.
6. Сравнить сетевое состояние до и после disconnect, аварии core, аварии UI и helper. Убедиться в удалении собственных маршрутов/фильтров и сохранении чужих настроек.

До выполнения этих пунктов отсутствие утечек, работа Telegram без прокси и crash rollback не считаются доказанными.
